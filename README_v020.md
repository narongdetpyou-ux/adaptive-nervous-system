# Adaptive Nervous System v0.2.0

## Capacity-Aware Decision Gate - ชุดทดลองพร้อมรัน

รุ่นนี้เพิ่มการประเมินกำลังประมวลผลจากประวัติคิวและงานที่ทำเสร็จ ก่อนอนุญาตให้ย้ายทรัพยากร ระหว่างขั้นตอน 3 ขั้น ภายใต้งบคงที่ 207 หน่วย ผล validation ลดงานค้างเฉลี่ยได้ **23.39% เทียบ Static** และ **39.34% เทียบ Persistent Gate รุ่นก่อน** แต่ยังแพ้ Static ใน 20 จาก 176 สถานการณ์ จึงเป็นต้นแบบการทดลองที่นำไปศึกษาต่อได้ ไม่ใช่ตัวควบคุมระบบจริงที่ผ่านการรับรอง

ไฟล์อ้างอิงหลัก: `report/ANS_v020_Report_TH.pdf`, `capacity_results/validation/summary.json`, `capacity_results/validation/episodes.csv`, `capacity_results/independent_review.json` และ `capacity_protocol.json`

## รุ่นนี้เพิ่มอะไร

มีตัวควบคุมใหม่สองแบบซึ่งต้องอ่านแยกกัน:

- `abc_capacity`: ให้ ABC เดิมเสนอคำสั่งหนึ่งคำสั่ง แล้วประเมินว่าจะยอมรับหรือคงทรัพยากรเดิม ถ้าไม่ผ่านจะไม่เปลี่ยนสถานะหรือเวลาล็อกภายใน ABC
- `capacity_aware`: ใช้แบบจำลองจัดอันดับคำสั่งทั้งหมดใน catalog เดิม เป็นตัวเลือกคำสั่งใหม่แบบ deterministic ไม่ได้อ้างว่าผลทั้งหมดเกิดจาก ABC เดิม

ทั้งสองแบบใช้การกระทำจาก catalog เดิมและมีตัวเลือก hold, เริ่มย้ายได้หลัง 5 นาที, เว้นการย้ายอย่างน้อย 8 นาที และคงทรัพยากรรวม 207 หน่วยเสมอ รุ่นใหม่ยังต้องเหลืออย่างน้อย 10 หน่วยต่อขั้น เป็นข้อจำกัดเพิ่มที่เข้มกว่า baseline เดิมซึ่งอนุญาตให้เหลือศูนย์ได้

### การประเมินกำลังจากสิ่งที่สังเกตได้

เมื่อจบนาทีแล้วคิวยังเหลือ แปลว่าในแบบจำลองนี้ขั้นนั้นใช้กำลังเต็ม จึงใช้ `flow / allocated_resources` เป็นค่าผลิตภาพที่วัดได้ แต่ถ้าคิวหมด อัตรานี้เป็นเพียงขอบล่าง: อาจมีงานให้ทำไม่พอ การแทนกำลังจริงด้วยค่าต่ำเช่นนี้จะทำให้ระบบตีความโหลดเบาเป็นเครื่องช้า

ตัวประมาณใช้ nominal prior 200 หน่วยงาน/นาที/หน่วยทรัพยากร ซึ่งเป็นสมมติฐานเดียวกับแบบจำลองเดิม เมื่อไม่มีงานพอให้วัดกำลังเต็ม จะปรับค่ากลับเข้าหา prior ทีละ 10% การฟื้นตัวนี้เป็นสมมติฐาน ไม่ใช่ข้อมูลที่สังเกตได้ ตัวควบคุมไม่ได้รับ true productivity, ป้ายกำกับสถานการณ์ หรือข้อมูลอนาคต

### เกณฑ์การอนุญาตคำสั่ง

จำลองผลของคำสั่งเทียบ hold ล่วงหน้า 8 นาที ครอบคลุมช่วงที่ห้ามเปลี่ยนคำสั่ง ใช้แบบจำลอง 9 แบบจากปริมาณงานเข้า 0.8/1.0/1.2 เท่าของค่าเฉลี่ยล่าสุด 3 นาที ร่วมกับอัตรากำลังแบบต่ำ, ค่าประเมินกลาง และการกลับสู่ prior แบบเส้นตรง

คะแนนคือค่าเฉลี่ยงานค้างที่คาดการณ์ บวก 0.25 เท่าของงานค้างปลายช่วง คำสั่งต้องลดคะแนนเฉลี่ยมากกว่า 10 หน่วยและ 2% ของ hold และต้องไม่แย่กว่า hold ในทั้ง 9 แบบจำลอง หากเสมอจะเลือก hold ก่อน สมมติฐาน 9 แบบนี้ไม่ครอบคลุมความเสียหายรูปแบบใดก็ได้ จึงไม่ใช่หลักประกันว่าจะปลอดภัยในเหตุการณ์ที่ไม่เคยจำลอง

## ผล validation ที่ตรึงก่อนประเมิน

- 11 กลุ่มสถานการณ์ กลุ่มละ 16 seed รวม **176 สถานการณ์ / 2,112 rollouts / 168,192 นาทีจำลอง**
- 5 กลุ่มอิง trace สังเคราะห์เดิม ใช้ seed ใหม่และเวลา 60 นาที; 6 กลุ่มสร้างรูปแบบโหลดใหม่ ใช้เวลา 96 นาที
- เปรียบเทียบทุก policy ด้วยงานเข้าและผลิตภาพชุดเดียวกัน ABC และ wrapper แบบสุ่มใช้ seed 11/29/47; เฉลี่ยทั้ง 3 seed ภายในสถานการณ์ก่อนรวมผล
- ช่วงความเชื่อมั่นมาจาก paired bootstrap 2,000 ครั้ง สุ่มสถานการณ์ภายในแต่ละกลุ่ม ข้อมูลนี้ยังเป็นสังเคราะห์ทั้งหมด

| วิธี | งานค้างเฉลี่ย | ค่าเฉลี่ยค่าสูงสุด | งานค้างเมื่อจบ | การย้ายเฉลี่ย |
| --- | ---: | ---: | ---: | ---: |
| Static 69/69/69 | 33,169.29 | 85,544.40 | 25,071.85 | 0.00 |
| MaxWeight-like | 60,999.21 | 146,581.37 | 59,411.08 | 9.68 |
| ABC เดิม | 52,921.45 | 125,655.36 | 43,115.03 | 9.63 |
| ABC + Persistent Gate | 41,892.08 | 100,249.78 | 38,790.57 | 5.34 |
| ABC + Capacity Gate | 29,203.76 | 74,736.62 | 24,489.52 | 2.19 |
| Capacity-aware selector | 25,411.84 | 67,392.56 | 24,414.03 | 4.32 |

เทียบ Static: Capacity-aware ลดงานค้างเฉลี่ย **23.39%**, ช่วง paired 95% bootstrap **20.76-26.32%**, ชนะ 139 / เสมอ 17 / แพ้ 20 สถานการณ์ เทียบ Persistent Gate ลด **39.34%**, ช่วง **36.92-41.81%**

ผลแยกแหล่ง: กลุ่ม trace เดิม 80 สถานการณ์ ลด **30.67%** เทียบ Static; กลุ่มโหลดสร้างใหม่ 96 สถานการณ์ ลด **22.42%** ช่วงความเชื่อมั่นเป็นความแปรผันภายในครอบครัวแบบจำลองที่กำหนด ไม่รวมความไม่แน่นอนจากระบบจริงหรือรูปแบบโหลดที่ไม่ได้สร้าง

ตัวกรอง ABC อย่างเดียวลดงานค้างเฉลี่ย **11.96% เทียบ Static** และใช้การย้ายเฉลี่ย **2.19 ครั้ง** ส่วนตัวเลือกทั้ง catalog ใช้ **4.32 ครั้ง** และงานค้างเฉลี่ยต่ำกว่าตัวกรอง ABC อีก **12.98%** จึงมีทั้งประโยชน์จากการกรองคำสั่ง และประโยชน์เพิ่มจากวิธีเลือกคำสั่งใหม่

### ข้อเสียที่ต้องเก็บไว้

กลุ่ม `surge_only` ไม่มี fault ของผลิตภาพ แต่โหลดพุ่งขึ้น: งานค้างเฉลี่ย Static 699.67 เทียบ Capacity-aware 832.59 เพิ่มขึ้น **19.00%** (เพิ่ม 132.93 หน่วย) แพ้ 11/16 กรณี ส่วน ABC + Capacity Gate เท่ากับ Static ในกลุ่มนี้

แม้ภาพรวมงานค้างปลายช่วง validation ลดลงเล็กน้อย แต่บางกรณีมีงานเหลือเพิ่ม เช่น `generated_switching_fault`, seed 1014: Static จบโดยไม่มีงานค้าง แต่ Capacity-aware เหลือ 10,879.58 หน่วย ผลเฉลี่ยจึงไม่ใช่หลักประกันรายสถานการณ์ งานค้างปลายช่วงแย่กว่า Static ใน 8/176 กรณี ผล development มีงานค้างปลายช่วงมากกว่า Static ด้วย ภาพรวม validation งานค้างปลายช่วงลดเพียง 2.62% และงานเสร็จเพิ่ม 0.128% จึงไม่ควรเรียกผลลดงานค้าง 23.39% ว่าเป็นการเพิ่ม throughput หรือเพิ่มกำลังประมวลผล 23.39%

ดูทุกกลุ่ม, ทุก seed, ค่าเฉลี่ยและช่วงความเชื่อมั่นเต็มใน `summary.json` และ `episodes.csv` ไม่มีการตัดกรณีที่แพ้ออก

## การตรวจความถูกต้อง

- **23 tests ผ่าน**: 8 tests เดิมและ 15 tests ใหม่ ดู `capacity_results/unit_tests.log`
- ต้นฉบับ 11 ไฟล์และข้อมูล input ตรง checksum; frozen ABC และ 5 ไฟล์ Neuron Flow ไม่แก้ไข
- บังคับสมดุลทรัพยากรและสมดุลงานทุกนาที ทุก rollout; ตรวจขอบเขตจำนวนแถวและการรวมผลทั้งหมด
- ตรวจการเล่นซ้ำด้วยเลขคณิตอีกชุดใน 66 representative traces รวม 5,256 นาที เลือก seed แรกของทุกกลุ่ม/ทุก policy ก่อนดูผล ไม่ได้อ้างว่า replay อิสระทุกนาทีของทุก rollout
- ผู้ตรวจอิสระสร้างตัวควบคุมใหม่จาก observations ใน 22 traces ของสอง policy ใหม่ แล้วได้คำสั่งและหลักฐานตรงกันทุก 1,752 การตัดสินใจ โดยไม่ป้อน true productivity
- Neuron Flow รันจริง 3 workers และ 6 agents; ทดสอบ transient failure ก่อนเริ่ม ABC Capacity rollout, retry สำเร็จ, ส่ง job ซ้ำ/เปิดใหม่ไม่ทำงานเดิมซ้ำ
- แก้ completed count +1 โดยเจตนา: validator ปฏิเสธ, งานที่พึ่งผลนั้นถูกบล็อก, งานอิสระยังสำเร็จ
- รัน validation ใหม่ทั้งหมดอีกครั้ง ได้ไฟล์ผลวิเคราะห์ 16 ไฟล์ตรงกันทุกไบต์ รวม summary, CSV, scenario manifest, trace index, trace.gz ทั้ง 6 ชุด และ rows JSON ทั้ง 6 ชุด ดู `capacity_results/reproducibility.json` การรันซ้ำไม่นับเป็นหลักฐานอิสระเพิ่ม

สามารถตรวจหลักฐานที่แถมมาซ้ำได้ด้วย:

```sh
python review_capacity_results.py --out capacity_results/validation
```

โปรโตคอลและ source hash ถูกตรึงในเครื่องก่อน validation ไม่ใช่การ preregister กับทะเบียนวิจัยภายนอก การไม่ปรับหลังดู validation ช่วยแยกการพัฒนาออกจากการตรวจชุดใหม่ แต่ไม่ได้รับประกันความเป็นกลางหรือความใช้ได้กับระบบจริงทั้งหมด

## ขอบเขตและการต่อยอด

โมเดลเป็นคิวของไหล 3 ขั้นต่อกัน งานอาจไหลผ่านหลายขั้นในนาทีเดียว ทรัพยากรแบ่งเป็นเศษส่วนได้ ไม่มี finite buffer, การทิ้งงาน, เวลาในการย้ายทรัพยากร, ค่าใช้จ่ายย้าย, overhead ของการตัดสินใจ หรือ sensor noise แบบระบบจริง ตัวเลขงานค้างไม่ใช่ p95 HTTP latency, throughput benchmark ของเซิร์ฟเวอร์ หรือผลจากลูกค้าจริง

สิ่งที่ควรทดสอบต่อคือการป้องกันการย้ายใน surge-only, ความเสียหายที่ย้ายตำแหน่งภายในช่วงล็อก 8 นาที และความแม่นยำของ capacity estimate เมื่อการฟื้นตัวถูกซ่อนด้วยงานน้อย ควรเริ่มจาก telemetry ที่อ่านอย่างเดียวและประเมินคำแนะนำเทียบเหตุการณ์จริงก่อนเชื่อมคำสั่งควบคุมทรัพยากร โครงการนี้ยังไม่ได้เชื่อมระบบควบคุมจริงหรือส่งคำสั่งภายนอก

แนวคิดการประเมินผลล่วงหน้าและตัดสินใจใหม่จาก observations อยู่ในแนวทาง model-based / receding-horizon control ซึ่งเป็นแนวคิดที่มีมาก่อน ดู Rawlings, Mayne, Diehl, *Model Predictive Control: Theory, Computation, and Design*, [เว็บไซต์ผู้เขียน](https://sites.engineering.ucsb.edu/~jbraw/mpc/index.html) รุ่นนี้เป็นการเลือก action คงที่จาก catalog ขนาดจำกัด ไม่มีการพิสูจน์ MPC stability/optimality และไม่อ้างว่าเป็นอัลกอริทึมใหม่ทางวิชาการ
