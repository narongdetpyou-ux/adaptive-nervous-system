# Shadow replay v0.3 - อ่านข้อมูลแล้วให้ข้อเสนอ

`shadow_replay.py` อ่านไฟล์การสังเกตที่บันทึกไว้ แล้วเรียกตัวควบคุม `V3Policy` ตามลำดับเวลา เพื่อแสดงว่าตัวควบคุมจะเสนอการย้ายแบบใดในแต่ละนาที การจัดสรรจริง คิว และการไหลของงานยังคงอ้างอิงเหตุการณ์ที่อยู่ในไฟล์เท่านั้น

ตัวอย่าง `synthetic_example.json` เป็น **ข้อมูลสังเคราะห์** จากเส้นทาง Static ในชุด development: `processing_slow`, seed 1000, regime `instant` รวม 92 นาที บันทึกนี้ไม่มีการย้ายจริง ได้ลบกำลังการผลิตจริงที่ซ่อนอยู่ (`productivity`) และหลักฐานการตัดสินใจเดิมออกแล้ว ข้อมูลนี้ไม่ใช่ telemetry จากบริการหรือลูกค้าจริง

## วิธีใช้

เรียกคำสั่งจากโฟลเดอร์โครงการ โดยใช้ไฟล์ผลลัพธ์ชื่อใหม่:

```bash
python shadow_replay.py --input synthetic_example.json --validate-only
python shadow_replay.py --self-test
python shadow_replay.py --input synthetic_example.json --out telemetry/shadow_recommendations.json
```

การ replay ปกติตรวจค่าเริ่มต้นของ `V3Config` และไฟล์โค้ดที่เกี่ยวข้องกับ protocol ที่ตรึงแล้ว หาก hash หรือค่าตั้งต้นไม่ตรง จะหยุดพร้อมข้อความระบุสาเหตุ โหมดนี้ใช้แพ็กเกจ v0.3 ที่ทำเสร็จแล้ว ส่วน `--self-test` อนุญาตค่าเริ่มต้นระหว่างการพัฒนาเมื่อยังไม่มี protocol เพื่อทดสอบตัว adapter ได้

ไฟล์ข้อมูลต้นฉบับไม่ถูกแก้ไข และผลลัพธ์ที่มีอยู่จะไม่ถูกเขียนทับ ตัว adapter ไม่มีการเชื่อมต่อบริการภายนอก ไม่มีการส่งคำสั่งปรับทรัพยากร และไม่ต้องใช้ API key

## รูปแบบข้อมูล

ดูโครงสร้างใน `telemetry_schema.json` และตัวอย่างครบชุดใน `synthetic_example.json` โดยวางข้อมูลตามเวลานาที 0, 1, 2, ... ไม่มีนาทีขาดหรือซ้ำ:

| ฟิลด์ในแต่ละ record | ความหมาย |
| --- | --- |
| `t` | ลำดับนาที เริ่มที่ 0 |
| `arrival` | งานจากภายนอกที่เข้าขั้นแรกในนาทีนี้ |
| `observed_queue` | คิวทั้งสามขั้นหลังรับงานเข้า และก่อนให้บริการ |
| `staff_before` | ทรัพยากรที่ผูกไว้กับแต่ละขั้นก่อนการย้ายจริงของนาทีนี้ รวมส่วนที่กำลังเดินทางเข้าขั้นนั้น |
| `actual_delta` | การย้ายที่เกิดขึ้นจริงในบันทึก ผลรวมต้องเป็นศูนย์ |
| `committed_staff` | ทรัพยากรที่ผูกกับแต่ละขั้นหลังการย้ายจริง |
| `active_staff` | ทรัพยากรที่พร้อมทำงานจริงในนาทีนี้ |
| `pending_staff` | ทรัพยากรที่กำลังเดินทางเข้า ยังให้บริการไม่ได้ |
| `flow` | งานที่แต่ละขั้นทำเสร็จจริงในนาทีนี้ |
| `end_queue` | คิวเมื่อจบนาที |
| `known_transit_delay` | เวลาขนย้ายที่ทราบ: 0, 1 หรือ 3 นาที ต้องคงที่ตลอดบันทึก |

ส่วน `initial_state` ระบุ committed allocation, คิวก่อนนาทีแรก และเวลาที่เกิดการย้ายจริงครั้งล่าสุด (`last_actual_change`) ตัวอย่างใช้ `-1000000000` เพื่อหมายถึงไม่มีการย้ายก่อนหน้าในช่วงที่เกี่ยวข้อง ต้องไม่มีทรัพยากรค้างระหว่างขนย้ายตอนเริ่มบันทึก

`units` ระบุหน่วยเป็น `minute`, `work_unit` และ `resource_unit` พร้อมคำอธิบายการแปลงหน่วยงาน ในตัวอย่าง หนึ่งหน่วยงานมาจากหนึ่งจำนวน request สังเคราะห์ ทรัพยากรเป็นหน่วยนามธรรม ไม่ใช่จำนวนเครื่องที่วัดจริง

## สมมติฐานที่ตัวตรวจต้องการ

บันทึกต้องตรงกับแบบจำลองคิวต่ออนุกรมสามขั้นของโครงการ:

- งานอาจผ่านหลายขั้นในนาทีเดียว การไหลที่ขั้นก่อนหน้าส่งต่อให้ขั้นถัดไปได้ทันที
- `active_staff + pending_staff = committed_staff` ทุกขั้น และงบรวมเท่ากับ 207
- การย้ายจริงใช้ catalog เดิม มี warmup 5 นาที, dwell 8 นาที และสำรองอย่างน้อย 10 หน่วยต่อขั้น
- การย้ายที่นาที `t` ทำให้ทรัพยากรขาออกหยุดให้บริการทันที ส่วนขาเข้าเริ่มทำงานก่อนให้บริการที่นาที `t + delay`
- คิวและ flow ต้องต่อกันได้โดยไม่สร้างหรือทำงานหาย ตัวตรวจไม่เดาความสามารถในการให้บริการจาก flow ที่น้อยเพียงอย่างเดียว

ข้อมูลจริงมักมีหน่วย ช่วงเวลาวัด การส่งต่อ และความคลาดเคลื่อนของเซนเซอร์ต่างจากแบบจำลองนี้ จึงต้องทำแผนการแปลงและตรวจความเข้ากันได้ก่อนใช้ ไม่ควรแก้ค่าข้อมูลให้ผ่านตัวตรวจโดยไม่มีเหตุผลที่ตรวจสอบได้

การตรวจ schema อย่างเดียวไม่ตรวจสมการข้ามนาทีทั้งหมด จึงควรใช้ `--validate-only` ซึ่งตรวจเพิ่มเติมทั้งลำดับเวลา สมดุลคิว ทรัพยากร การขนย้าย catalog และ dwell

## ทำไมข้อเสนอที่ไม่ถูกใช้ต้องไม่เลื่อนนาฬิกา

ในแต่ละนาที adapter ทำงานตามลำดับนี้:

1. เรียก `decide` หนึ่งครั้ง จากคิวและข้อมูลที่สังเกตแล้วเท่านั้น
2. คืนค่า `last_change` ที่ตัวควบคุมอาจเปลี่ยนเพราะข้อเสนอสมมติ
3. อัปเดต `last_change` เฉพาะเมื่อ `actual_delta` ระบุว่ามีการย้ายจริง
4. เรียก `observe` หนึ่งครั้ง ด้วย **active resources จริง** พร้อม flow และคิวที่บันทึกไว้
5. นาทีถัดไปใช้ allocation ที่เกิดขึ้นจริงต่อจากบันทึก

ตัวอย่าง Static ให้ข้อเสนอการย้าย 13 ครั้งในการทดสอบ adapter แต่ไม่มีการย้ายจริงเลย จึงอาจเห็นข้อเสนอซ้ำในนาทีติดกันได้ นี่เป็นพฤติกรรมที่คาดไว้เมื่อข้อเสนอก่อนหน้าไม่ถูกใช้ **13 ข้อเสนอไม่ใช่แผนการย้าย 13 ครั้งที่นำไปปฏิบัติตามลำดับได้ทันที** หากเริ่มทำจริง ข้อจำกัด dwell และคิวในอนาคตจะเปลี่ยนไป

`--self-test` ตรวจว่าข้อมูลต้นฉบับไม่เปลี่ยน ข้อเสนอที่ไม่ถูกใช้ไม่เลื่อนนาฬิกา และตัวอย่างการย้ายจริงที่นาที 5 ทำให้นาฬิกาและช่วงล็อกเปลี่ยนตามการกระทำนั้น

## อ่านผลลัพธ์อย่างไร

ผลลัพธ์แต่ละนาทีมี `recommended_delta`, `reason`, `recorded_actual_delta`, นาฬิกาการย้ายจริงก่อน/หลัง และ `model_evidence` ของข้อเสนอที่คำนวณใหม่ ฟิลด์ `recommendation_applied_by_adapter` เป็น `false` เสมอ

`input_canonical_sha256` เป็น hash ของข้อมูล JSON ที่จัดลำดับ key อย่างคงที่ ส่วน `input_file_sha256` ในผลจาก CLI เป็น hash ของ byte ในไฟล์ที่อ่าน

ตัวเลขที่มีชื่อ `predicted_...` เป็นค่าจากแบบจำลอง ไม่ใช่ผลที่เกิดขึ้นจริงเมื่อทำตามคำแนะนำ บันทึกจริงจะเปลี่ยนหากนำข้อเสนอไปใช้ ดังนั้น replay นี้ **ยังวัดไม่ได้ว่าข้อเสนอจะลดงานค้าง เพิ่ม throughput หรือประหยัดทรัพยากรได้เท่าไร** ต้องใช้การประเมินแบบจำลองหรือการทดลองที่เหมาะสมแยกต่างหาก

ไฟล์ shadow adapter และตัวอย่างถูกจัดไว้เป็นส่วนใช้งานต่อของแพ็กเกจ ไม่ได้ใช้เปลี่ยนผลหรือปรับนโยบายของชุด validation ที่ตรึงแล้ว
